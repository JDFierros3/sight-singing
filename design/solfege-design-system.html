“Shape-notes memorized?” drives the setlist. The shapes are the foundation everything else reads off, so the session generator branches on this answer: Not yet → the session opens with a short shape-note flashcard primer (see Flashcards) before the first warm-up, and lesson 1 is pulled in. Yes → that primer is skipped entirely and the session goes straight to warm-ups. Stored locally like the rest of the profile, so returning singers aren't asked again (until they clear it or flip it in settings).

▸ Advanced
Desktop spreads the state across a persistent rail + inspector; mobile stacks it under a bar with a bottom nav. Same engine, two layouts.

No backend — everything persists locally. This app is a purely static site with zero server. All continuity — the saved voice profile (Do, range, part, sensitivity), the current session and which step you're on, the streak and completion history, and last-used settings — is stored in localStorage (with a cookie fallback), keyed under a single namespace (e.g. solfege.v1.*). There are no accounts and no sync: a session is resumable on the same device/browser only, and clearing site data resets it. Design implication — the streak is per-device, "Resume session" reads from local storage, and nothing ever requires a network round-trip.

Using this file

How to treat this document

Canonical UX reference. Lives at design/solfege-design-system.html and is published as an artifact. Future work — and future Claude sessions with fresh context — read this as the source of truth for layout, component names, shapes, colours, and the mobile-vs-desktop split. The classes here (.sn .sessbar .card .rail .inspector .quiz .stave .sheet) are the component vocabulary; the shape sprite (#sn-do … #sn-ti) matches js/rendering/shapes.js. If we later host a formal design system, these push to a Claude Design project.

Schematic fidelity — real labels, real shape-notes, approximate spacing.
